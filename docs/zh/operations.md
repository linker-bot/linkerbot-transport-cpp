## 运行配置与部署

固定 transport/hand 版本、进程架构、编译器/CRT、驱动和固件组合，保留来源 SHA 与
`build-info.json`。Linux ARM64 能编译本库，不代表某份 x64 厂商库可加载；厂商依赖需单独确认。
SocketCAN 的接口/速率由系统配置，SLCAN 的串口和 profile 显式传入，不做全机扫描或固件猜测。

MiniCANFD 和 PCAN 的库选择优先级为配置参数 → 各自环境变量 → 平台默认搜索。
变量分别为 `LINKERBOT_CANFD_LIB`、`LINKERBOT_PCAN_LIB`；它们仅在创建/加载时读取，
修改环境不会替换存活连接。重连 factory 应捕获已核对的配置和库路径，避免恢复时意外换库。
空环境变量按未设置处理；空显式路径报校验错误。其他默认值见各后端与 [构建选项](build.md)。

本库没有守护进程、数据库、Redis、自动日志文件或持久卷需求，也不保存幂等键/确认记录。
如果上层把日志、设备身份、校准、命令历史或业务确认写到文件/数据库，容器部署时应由上层
配置持久卷或远端存储、访问权限和保留策略。停止/重建进程不会自动恢复本库的内存 inbox、
排队任务或回执；不得把它们当作可靠持久队列。

容器应只提供实际使用的接口：SocketCAN 依赖可见的 CAN 网络接口，SLCAN 依赖指定串口，
厂商后端依赖匹配库/驱动。不要把整机设备目录和全部环境变量传入应用作为通用排障办法。
系统服务的退出宽限时间应覆盖正常驱动返回与资源清理；异常驱动的不可取消调用仍可能超时。

## 共享、退出与异常清理

设备需要独立生命周期时，使用 `TransportRuntime` 和每设备一个 `DeviceSession`。关闭一个设备
只结束其自身工作、订阅和计数租约，其余设备继续连接；最后一个设备释放通道。重试所有权和
协调恢复见[设备会话](device-sessions.md)。

以下为直接共享原始 Session 的兼容接口规则：Session 不是每个调用者独立的连接句柄。
共享使用者中任一方 `close()` 会关闭整个会话、清理该会话持有的资源，并使其他使用者的 inbox 失效；
外部总线或借用 dispatcher 的所有权不因此转移给 Session。
每个设备结束时优先关闭自身 inbox、取消自身 endpoint；最后由统一的所有者关闭 Session。

退出顺序为：停止上层生产新任务 → 取消不再需要的 endpoint → 核对在途回执/业务状态 →
关闭 inbox/Session → 处理可重试的关闭错误 → 释放借用的 dispatcher 或外部 bus。
回调内不能同步调用 Session close/recover；借用 dispatcher 的延迟清理在销毁 dispatcher 前
由外部线程调用 `Session::drain_deferred_cleanup()` 等待。

厂商物理关闭或 Exit 失败时，保留原持有者并重试；不要通过清空资源表、丢弃占用标记或
换一个通道键来伪装释放成功。后端提供的 deferred cleanup 只在当前进程内保留资源归属，
不是磁盘恢复日志，也不能保证进程被强杀后驱动已完成释放。

## 断连与确认丢失

先保存错误、generation、回执的接受帧数及不确定性，停止不安全的新控制任务。
有 factory 的 Session 可用观测到的 generation 执行 recover；成功后旧路由关闭、未完成任务取消，
不自动重放控制帧。重新注册路由、枚举/核验设备身份与实际状态，再恢复业务。

业务确认丢失不代表设备没有执行。需要人工核对的场景包括：当前帧不确定、设备重启后身份变化、
驱动长时间阻塞、历史命令与当前状态不一致。由设备协议决定哪些命令可幂等重试，不能只改请求键、
放宽身份校验或删除旧确认记录来强行继续。通信库不提供跨进程、跨重启的恰好一次执行保证。

## 升级顺序

1. 记录当前可回退的源码/包、SHA256、编译器/CRT、驱动/固件、通道和业务配置；
   上层持久化的旧日志、校准和确认记录按其保留策略备份，勿因升级删除。
2. 在新构建/安装前缀验证新 transport；先跑离线测试，再编译配套 hand 和实际应用。
   `0.3.x` hand 要求 transport SDK 版本不低于 hand 补丁版本；遵守 `SameMinorVersion` 和配套重编译要求。
3. 停止上层写入和控制生产者，等待/核对在途操作并完成原持有者清理；不要在活动进程中替换 DLL。
4. 切换完整的应用、头文件、静态库、运行库和配置组合。驱动/固件单独变更时重新验收，
   不把源码层通过沿用为新驱动的实机结论。
5. 启动后核对库实际路径、包来源、设备身份、generation、读取和有限控制操作，保存验收日志。
   有先后依赖的 PR 或 SDK 更新按依赖顺序集成，再验证后续应用。

## 回滚限制

回滚应恢复整套经过验证的应用、hand、transport、CRT 与配置，重新编译或使用原配套产物；
不能只换头文件或把旧静态库接到新二进制。驱动/固件回退是否支持由厂商决定。
切换前仍要停止新命令并完成资源清理；回滚不撤销设备已经执行的动作，也不会复原旧 generation。

本库没有持久化 schema 迁移；若上层升级了记录格式，需要它自己的兼容读取、人工核对及
回滚方案，旧日志和确认记录应保留。原始诊断字段/历史日志不得因本轮文档或库更新而自动清除。

## 交付与发布核验

已发布的下载入口、校验命令及文档勘误见[发行指南](releases.md)。

独立分支、签名提交和英文 PR 应说明本轮变化、兼容性、复现命令与 Linux 结果。
检查最新 head 的 CI、review 和未解决线程；合并后同步 main 并重新验证，清理本轮分支/临时环境。
正式发布时再更新 Changelog、使用签名标签并通过已确认的发布流程产物化；目前 CMake/CPack
只提供构建和打包能力，不自动发布 GitHub Release。

Linux GCC Release 任务保留 amd64、ARM64 的 CPack TGZ 及相邻 SHA256 文件；Windows
任务保留 x64/ARM64 Debug/Release ZIP 及其 SHA256 文件。正式发布应使用签名标签所指精确提交的
成功运行，不得将带覆盖率插桩的 Linux Debug 构建作为 Release 包发布。上传前核对每个包的
`build-info.json`、二进制架构和移动目录后的安装消费者。发布已核验的压缩包、汇总的
`SHA256SUMS.txt` 和英文 Release Notes，随后重新下载 Release 附件核验。
标签标识源码提交，校验值标识实际上传的字节。

发行前后核对 Release 是否稳定版、正文、附件、SHA256、来源 SHA、配置、二进制架构和安装消费。
本仓库没有镜像发布/签名流程，不能宣称 SDK ZIP 或 TGZ 带有容器镜像签名；如由上层交付镜像，
须单独核验构建来源和签名。不要把推送标签或 CI 上传附件当作发布完成。
